How valet works

valet lets a script or a coding assistant use a password, token or login from your vault without ever holding it in its hands, the same way an SSH agent signs for you without handing out your private key.

The idea in four lines

  1. The caller asks for an action by credential name: "GET this URL with CRM API", "run hostname on the build server".
  2. valet looks the item up in one vault collection (Agent), checks the target is one the item allows, and shows you an approval popup if the item's policy asks for one.
  3. valet does the sign-in itself: injects the token, answers the Windows challenge, types into the form, opens the SSH or WinRM session.
  4. The caller gets the result back. Anything that echoes the secret is replaced with [REDACTED:CRM API], and one line goes into the audit log.

Three ways in

WhoHowSecret ever in the caller?
Coding assistantMCP tools: http_request, browser_login, ssh_exec, win_exec, sql_query, rdp_open, check_credentialsNo

Example: a script that needs a password

Say you write sync_contacts.py, which signs in to SQL Server and an API. The usual shortcut is to paste the password into the file. With valet, the file only names which vault item it needs.

Before: password in the file

import pyodbc

conn = pyodbc.connect(
  "SERVER=sql01;UID=sync;"
  "PWD=Summer2026!")

After: read it from the environment

import os, pyodbc

conn = pyodbc.connect(
  "SERVER=sql01;UID=sync;"
  f"PWD={os.environ['SQL_PASS']}")

Then say where SQL_PASS comes from. Either on the command line:

python -m valet run -e SQL_PASS=valet://SQL sync/password -- python sync_contacts.py

or in a .env file that is safe to commit, because it holds references and no secrets:

# .env
SQL_PASS=valet://SQL sync/password
API_TOKEN=valet://Contacts API/password
API_URL=https://contacts.example.com     # plain values pass through unchanged
python -m valet run --env-file .env -- python sync_contacts.py

What happens when you press Enter

  1. valet finds every variable whose value starts with valet://. The part before the last / is the item name, the part after it the field: password, username, totp (the current code), uri, or any custom field.
  2. For each item it asks your approval once (default: once a day per item; set broker_approval to never for unattended jobs, always for sensitive ones). The popup shows the item and the exact command line.
  3. It starts the command with the real values in its environment, and removes BW_SESSION so the script gets its own secrets and not the key to the whole vault.
  4. Every line the script prints goes through the redactor, so a stray print(password), a stack trace or a debug log shows [REDACTED:SQL sync]. The exit code is passed on.
  5. The audit log gets a line: time, item names, command, ok or refused.

The same works for any language, because every language reads environment variables:

# PowerShell
$cred = New-Object PSCredential 'CORP\sync', (ConvertTo-SecureString $env:SQL_PASS -AsPlainText -Force)

# Node
const token = process.env.API_TOKEN;

# Bash
curl -H "Authorization: Bearer $API_TOKEN" "$API_URL/contacts"

Better still, when a coding assistant runs the job: if the script only calls an API, let the assistant call http_request directly, and if it only runs commands on a server, use ssh_exec or win_exec. Then no process outside valet ever holds the secret at all. valet run is for code that really needs the value itself, such as a database driver.

Setting up a vault item

An item is an ordinary login in the Agent collection. Its URIs say where it may be used, and the scheme of each URI says how:

URIUsed byNotes
https://api.example.comhttp_request, browser_login exact host; https://*.example.com for subdomains
ssh://10.0.0.5ssh_execpassword SSH; host key must be in known_hosts
winrm://10.0.0.6win_execPowerShell over WinRM, NTLM, port 5985 (winrms:// for 5986)
mssql://10.0.0.7sql_queryDOMAIN\user = Windows auth, otherwise a SQL login
rdp://10.0.0.6rdp_openopens Remote Desktop for you, already signed in
10.0.0.8 (no scheme)check_credentialsprobed for ssh, WinRM and SQL Server; tells you which scheme to add

One item can list several URIs: a Windows server login might carry winrm://, rdp:// and mssql:// for the same host. A password is never sent to a host or protocol the item does not list.

Custom fieldValues
broker_authweb only: bearer (default), basic, header:<Name>, query:<param>, form, ntlm
broker_approvalnever, daily, always
broker_allow_httpyes to allow plain http (trusted network only)
broker_trust_certyes to accept a self-signed certificate (SQL Server, WinRM over https)

After an import: find the wrong passwords

Bulk imports from old notes are never perfect. Instead of retyping everything, run

python -m valet check

It approves once, tries every item's sign-in and prints ok, failed or skipped per URI. Fix only the failed ones in the vault, then run it again.

What it does and does not protect

ProtectedNot protected
Secrets stay out of the assistant's context, transcripts and logs valet runs as your Windows user: a hostile program running as you can read what valet can
A credential only goes to the hosts and protocols listed on its item A script started with valet run holds the real value and could write it somewhere other than its output
Only the Agent collection is visible; the rest of the vault does not exist for valet The shared browser keeps the session cookie after browser_login, which is the point
Approval popups and an audit trail of every use
RDP passwords are stored as Windows domain credentials, which ordinary programs cannot read back

In short: valet keeps honest automation from ever seeing secrets, and makes every use visible. It is not a sandbox against malicious code running as your own user. For that, run the broker as a separate account or on another machine.
